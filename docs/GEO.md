# AI Discoverability (GEO)

**Last updated:** 2026-10-01

Aviary's `geo` checker reports observable controls and page signals that can matter to AI-assisted search and retrieval. It does not estimate rankings, predict citations, or claim that a page will appear in a generated answer.

The batch score summarizes configured checks; it is not a GEO readiness score. Some GEO profiles surface review signals without failing a check, so inspect the sitewide summary and opportunity review even when the average score is 100.

The [output-quality validation](GEO_OUTPUT_VALIDATION.md) compares actual checker and export outputs with official Google, OpenAI, and Bing documentation. It records source-derived cases, corrected interpretation errors, and the limits of the evidence. Passing diagnostics do not establish content truth, support from linked sources, or future citations.

## Coverage and limits

Aviary has a broad GEO workflow for live page diagnostics, robots and crawler-policy review, source/render comparisons, sitewide summaries, audit baselines, access-log analysis, and offline analysis of first-party exports or manually recorded answer citations. The provider-observation tools analyze the sample supplied by the operator; they do not automatically query every proprietary answer engine or predict future rankings and citations. Useful product work remains, including broader provider data integrations and more large-scale scan optimization.

For a single offline tour, run `pnpm run geo:toolbox:synthetic`; it creates ten independent synthetic GEO reviews under `reports/geo-toolbox/` and an `index.html` that links to each dashboard. Pass `-- output-directory` to choose another location. The individual package commands let you rerun one analysis at a time. Synthetic inputs illustrate report semantics only; use your retained answer observations for operational decisions.

The `pnpm run geo:*` examples in this guide invoke bundled workflow scripts, not flags on the `aviary` CLI. Run them from a source checkout, or invoke one from an npm install with `npm explore @ru1vly/aviary -- npm run <script> -- ...`. Use absolute input and output paths when running scripts from the installed package.

Turn an actual sitewide audit summary into a prioritized Markdown review with explicit scope and evidence notes using `pnpm run geo:opportunity-review -- reports/geo-summary.json reports/geo-opportunities.md`. Add `--audit reports/batch.json` to include the exact URLs and measured source/rendered-text agreement values for pages below the review threshold (currently 60%, used only to prioritize manual review), plus page-level author/date and answer-structure evidence. When available, the review records navigation readiness and settle-delay values from those page reports for reproducibility. It also summarizes observed crawler controls, citation evidence, external source links, and selected structured types. It does not predict rankings or citations; inspect the page reports before applying recommendations.

Compare matching routes across two hosts with `pnpm run geo:render-parity -- reports/primary-batch.json reports/mirror-batch.json reports/render-parity.md`. It pairs normalized paths and query parameters, then compares source/rendered phrase coverage and word counts on shared routes. Inputs can be CLI batch JSON or the full job JSON returned by the REST API. Run both audits with the same checker categories, `navigationWaitUntil`, and `settleAfterNavigationMs`; the tool rejects mismatched scopes/timing and does not assume the paired pages have identical content. Use CLI `--settle-ms` or REST `settleAfterNavigationMs` (0–30000 ms, default 1000) when client-side rendering needs time beyond the navigation readiness event.

For a complete two-host capture from URL lists, run `pnpm run geo:live-host-review -- first-urls.txt second-urls.txt reports/host-review [1500] [domcontentloaded]`. The runner audits both lists with the same navigation settings, then writes JSON and HTML reports, sitewide GEO summaries, prioritized opportunity reviews, and a route parity report. In a source checkout, run `pnpm run build` first so `dist/cli.js` exists. The workflow expects comparable routes; unmatched routes are reported rather than treated as failures.

## Plan a balanced prompt capture panel

Run `pnpm run geo:prompt-plan:synthetic` for a sample, or `pnpm run geo:prompt-plan -- answers.json reports/prompt-plan example.com` to plan follow-up captures from your observations. The bundle writes provider/cohort quotas as CSV, a paired-provider effort summary, versioned JSON, and an offline `index.html`. By default each provider/cohort is planned to at least 20 unique prompts; set `GEO_PROMPT_PLAN_MIN_PROMPTS` to change that floor. Supplying `example.com` enables owned-reach planning with a worst-case nominal 95% Wilson half-width of five percentage points; tune it with `GEO_PROMPT_PLAN_OWNED_REACH_MARGIN`.

Set `GEO_PROMPT_PLAN_MIN_JACCARD` (0.5–0.99) to request additional identical prompt groups until each pair's per-cohort exact-prompt Jaccard reaches the floor. Set `GEO_PROMPT_PLAN_MAX_TOTAL_PAIRED_GROUPS` to bound follow-up effort across provider pairs, and `GEO_PROMPT_PLAN_TOTAL_ALLOCATION=proportional` to allocate that cap by demand rather than evenly. `GEO_PROMPT_PLAN_COHORT_TARGETS` can point to a version 1 target file such as [this example](../examples/geo-answer-prompt-cohort-targets.example.json); `GEO_PROMPT_PLAN_FAIL_ON_MISS=1` makes unmet quotas, overlap floors, precision targets, or paired-group limits fail after the plan is written. The JSON output follows [the prompt-plan schema](geo-answer-prompt-sampling-plan.schema.json). This plans a balanced panel from observed cohorts; it does not estimate query demand or make a hand-selected sample representative.

## Citation repeatability across repeated captures

Run `pnpm run geo:repeatability -- observations.json reports/citation-repeatability.csv` to compare adjacent captures of the same exact provider, prompt, model, surface, locale, topic, and intent. The command also writes versioned JSON and a self-contained HTML review beside the CSV. Inputs are capped at 100 MiB and 200,000 observations; the HTML has a skip link and filterable table, displaying up to 500 provider/context rows, while CSV and JSON retain all rows. URL matching removes query strings and fragments; metrics show full citation-set and top-three Jaccard for exact URLs and source domains, rank-biased overlap (RBO, p=0.9) for ordered URL and domain lists, and median capture gap. The URL/domain split distinguishes page turnover from stable publisher coverage, while RBO emphasizes rank changes near the top. Add repeatable `--owned-domain example.com` options for owned-citation presence agreement and first-position persistence. Each exact prompt contributes one mean after its eligible adjacent pairs are averaged, and percentile-bootstrap intervals resample prompts with up to 2,000 deterministic draws. A global 10-million prompt-metric sample budget reduces the draw limit on large reports; intervals are withheld when fewer than 100 draws fit, while point estimates remain. The JSON records the draw limit and budget capacity; per-metric interval states show which intervals were estimated. Pairs with either `citationListComplete: false` are excluded and counted; prompts without an eligible adjacent pair remain visible in support fields. Unmarked lists at the 50-URL capture limit are treated as incomplete. Invalid citation URLs are counted and cause their capture list to be treated as incomplete; malformed observation rows are counted as skipped. This describes repeatability in the supplied capture panel, not provider-wide behavior. See [the report schema](geo-citation-repeatability.schema.json) and [synthetic input](../examples/geo-citation-repeatability.synthetic.example.json).

The command also writes `<output>-prompts.csv` with prompt-level means and exclusion counts. It uses a deterministic SHA-256 ID for each trimmed exact prompt and does not export prompt text; the hash is stable and may be guessable for common prompts, so treat it as pseudonymous data.

The standalone command accepts input files up to 100 MiB and panels up to 200,000 observations; `pnpm run geo:repeatability -- --help` prints its usage.

RBO uses deduplicated normalized URL or first-occurrence domain lists with `p=0.9`; for the finite lists, the remaining tail weight is assigned the final observed prefix overlap. The estimator string and parameter are included in the JSON method metadata. Captures with identical timestamps are not ordered arbitrarily: same-time pairs and adjacent transitions touching duplicate timestamps are excluded and counted. Each provider/context row includes its observed UTC start/end and median gap so you can see the sampled window behind its metrics.

Citation URL identity lowercases the host, strips a terminal host dot and default port, removes query/fragment data, and trims trailing non-root path slashes. Invalid or non-HTTP(S) values, or non-Boolean `citationListComplete` flags, are counted and make that observation's citation list incomplete.

Run `pnpm run geo:repeatability:synthetic -- [output-directory]` to generate and inspect the sample CSV, JSON, and HTML without supplying your own observations.

Compare two prompt-detail exports with `pnpm run geo:repeatability:compare -- baseline-prompts.csv current-prompts.csv reports/repeatability-change.csv`. It pairs SHA-256 prompt IDs only within the same provider and recorded context, reports current-minus-baseline prompt-level metric deltas, prompt gain/loss support, cluster-bootstrap intervals, and an exact two-sided sign test of non-tied prompt directions with Holm adjustment across the complete provider/context/metric family. The sign test uses the 50/50 positive-versus-negative null for independent prompt clusters; lexical duplicates or other prompt dependence can weaken that assumption. A five-million-term work cap suppresses the entire sign-test family rather than emitting partial adjusted p-values. One-sided prompts and shared prompts without a comparable metric remain explicit. It writes CSV, versioned JSON, and offline HTML; the aggregate GEO bundle runs this comparison automatically. When owned-citation metrics are enabled, prompt-detail exports include a hash of their normalized owned-domain set and the comparator rejects mismatches.

For automated regression monitoring, configure exact provider/context rules in JSON and run `pnpm run geo:repeatability:gate -- reports/repeatability-change.json examples/geo-citation-repeatability-gate.example.json reports/repeatability-gate.json`. A rule can scope a metric to a provider/context, set its largest acceptable decline and minimum number of paired prompts, then fails when the upper bound of the comparison's nominal 95% prompt-bootstrap interval is at or below that negative threshold. Add `"requireHolmSignTest": true` to also require a report-wide Holm-adjusted exact sign-test p-value at or below `alpha` (default 0.05). The interval remains nominal; the optional Holm check adjusts sign-test evidence across provider/context/metric rows, not across different rule definitions. Rules that match several context rows are evaluated row by row, so prefer narrow selectors for confirmatory CI gates. Missing matches, too little support, and unavailable intervals are explicit `inconclusive` results and exit nonzero alongside `failed`, so an unsupported comparison cannot silently pass CI. The rules use [the config schema](geo-citation-repeatability-gate-config.schema.json), and output follows [the gate schema](geo-citation-repeatability-gate.schema.json). `geo-citation-repeatability-gate.example.json` shows an exact-context rule; the adjacent synthetic comparison/config fixtures illustrate supported-decline and underpowered-result records.

For a manually dispatched GitHub Actions workflow that preflights panel comparability, builds both repeatability reports, compares them, runs the gate, posts a job summary, and uploads artifacts even on failure, see [the workflow template](../examples/geo-citation-repeatability-gate.github-actions.yml). Enable its `fail_on_panel_warnings` dispatch input to fail the workflow after reports are saved if the panel preflight raises any warning. Set its observation and rule paths to your retained capture files; it does not collect answers from providers.

## Check panel comparability before interpreting change

Before comparing capture periods, run `pnpm run geo:panel:compare -- examples/geo-answer-observations.baseline.example.json examples/geo-answer-observations.example.json reports/panel-preflight` (replace the sample paths with your retained captures). It writes context-stratum, prompt-ID, context-dimension, structured warning-code, and day-level capture-timeline CSVs, a versioned JSON report, and a searchable offline HTML overview capped at 500 context rows; the full CSV and JSON retain every row. Each input is capped at 100 MiB and 20,000 observations; those limits and the HTML row cap are recorded in the report. It checks exact provider/model/surface/locale/topic/intent balance, per-context observation-share shifts and total-variation context-mix change, exact-prompt overlap, per-dimension metadata coverage (per observation, so repeated captures count separately), capture depth, its coefficient of variation (standard deviation divided by mean captures per prompt), and Kish effective prompt sample size (total captures squared divided by summed squared per-prompt capture counts, so repeated captures contribute less; the companion capture redundancy factor is total captures divided by effective sample size and equals 1× when every prompt group has one capture; largest-prompt share shows the highest per-prompt fraction of captures; a configurable warning defaults to over 30% in any context), baseline/current capture-window lengths, inter-period gap, and largest within-panel gap between distinct UTC timestamps plus each context’s distinct timestamp and UTC-date counts and mean valid observations per observed UTC date. The timeline CSV aligns baseline/current captures by exact context and UTC date, with observation counts, distinct exact prompts, distinct capture instants, and citation-list completeness. It also checks incomplete citation-list shares and exact duplicate capture rows. Each window runs from that context’s earliest to latest valid UTC observation; an overlap has a zero-day gap, otherwise the gap is the distance between the nearest endpoints. Contexts found in only one panel have no period-gap value. Duplicate rows are counted and warned about but retained in every denominator so you can decide whether the source export should be cleaned. Observation-mix total variation is half the sum of absolute percentage-point shifts across all context strata, so 10 pp indicates that 10% of observation share would need to move between strata to align the mixes. A second prompt-mix total variation repeats that calculation using unique exact prompt groups instead of capture counts, separating prompt allocation changes from repeated-capture depth. Prompt text, answer text, and input path strings are not copied into outputs; the prompt CSV contains SHA-256 IDs, and CSV cells beginning with spreadsheet formula characters are escaped. By default it flags 10 pp per-context share shifts or observation/prompt-mix total variation, under 50% prompt Jaccard, above 10% incomplete lists, any exact duplicate capture rows, above 80% single-capture prompts, above 30% of captures from a single prompt in any context, below 80% optional context-dimension coverage, under 10 matched prompts in a context, a capture-window gap over 180 days, and any within-panel capture timestamp gap over 180 days; effective thresholds are recorded in the report. This is a descriptive preflight: it does not reweight a changed panel, declare a sample representative, or decide that a capture comparison is valid. Review context shifts, effective prompt sample size, and support before interpreting downstream GEO metrics; effective sample size and redundancy factor are descriptive and are not statistical sample-size guarantees. The optional `--fail-on-warnings` flag writes all artifacts, then exits nonzero if any advisory threshold is raised; warning-gate status is recorded in the JSON. The JSON contract is [geo-panel-comparability.schema.json](geo-panel-comparability.schema.json).

Use `--thresholds-file examples/geo-panel-comparability-thresholds.example.json` to load a version 1 profile and adjust numeric warning cutoffs; omitted values retain built-in defaults, unknown keys fail validation, and the effective thresholds plus whether they came from defaults or a profile are recorded in JSON. The profile can also list `failOnWarningCodes` to gate selected diagnostics; missing-stratum and malformed-row warnings remain active regardless of threshold settings. `warningDetails` adds stable warning codes with the observed value, cutoff, and unit while preserving the human-readable `summary.warnings`; it is optional in the report schema for compatibility with existing version 1 reports. The offline HTML shows those facts beside the active threshold table and profile source. The profile contract is [geo-panel-comparability-thresholds.schema.json](geo-panel-comparability-thresholds.schema.json). The bundle accepts `GEO_PANEL_COMPARABILITY_THRESHOLDS_FILE` and copies the selected profile into its checksum manifest; the GitHub Actions workflow has an optional `panel_thresholds_file` input. These values tune descriptive review flags and do not change estimates or make warnings statistical tests.

For a customized CI gate with a spreadsheet-friendly diagnostic export:

```sh
pnpm run geo:panel:compare -- baseline.json current.json reports/panel \
  --thresholds-file examples/geo-panel-comparability-thresholds.example.json \
  --fail-on-warnings
```

Repeat `--fail-on-warning-code context-share-shift`, `--fail-on-warning-code capture-window-gap`, `--fail-on-warning-code prompt-capture-concentration`, or `--fail-on-warning-code within-panel-capture-gap` to fail on chosen warning codes; a profile can instead set `failOnWarningCodes`. `--fail-on-warnings` still gates every advisory warning. `warningGate.mode` and `selectedCodes` identify the policy; `failedCodes` lists triggered gates, while `warningCount` remains the total diagnostic count. The warning CSV marks each diagnostic as selected or failed by the active gate and is written even when the gate fails, along with the context, prompt, dimension, JSON, and HTML reports.

## Repeatable answer-citation review

## Run the GEO checks

Run GEO alone:

```sh
aviary -u https://example.com/article --preset geo --markdown reports/geo.md
```

The `basic` preset disables GEO. The `advanced` and `strict` presets enable it with informational severity. Use `--preset geo` to run only the GEO checks, with informational severity, without enabling broader SEO checkers. Without a preset, the default full audit includes GEO.

The built-in search and data-use crawler lists can be extended with per-rule options. Custom tokens are matched against `robots.txt` and page directives as written; this does not verify that a service operates a crawler with that name. Supply an explanatory `purpose` for each custom data-use token.

For a single-page GEO audit snapshot comparison, run `bash examples/geo-single-page-baseline-comparison.sh current.json baseline.json`. Add the optional `output-dir` and `gate` arguments to choose an output folder and enforce `--fail-on-geo-change`; a failed gate exits 1 after writing its artifacts. After `gate`, pass repeatable `signal=<label>`, `url=<exact-url>`, and `transition=<before=>after>` selectors after `gate` to restrict change failures. The script regenerates HTML, PDF, Markdown, JSON comparison, and GEO-change CSV artifacts offline from the saved audits; when `gate` is requested it also saves the filtered, versioned decision as `geo-gate.json`; the report describes snapshot differences and does not predict citations.

For a saved batch audit, run `bash examples/geo-batch-offline-baseline-comparison.sh current-batch.json baseline-batch.json`. ## What Aviary reports

- **Search crawler access:** Evaluates the audited URL's path against `robots.txt` rules for Googlebot, bingbot, Amzn-SearchBot, Applebot, OAI-SearchBot, Claude-SearchBot, PerplexityBot, and MistralAI-Index. For each bot it reports the selected user-agent group and most-specific matching allow/disallow rule with its line number. Applebot supports Apple search experiences; Apple documents Applebot-Extended separately as a data-use policy token that does not crawl webpages. It reports robots policy only; it cannot verify CDN or firewall behavior, authentication, actual crawling, indexing, or inclusion in answers.
- **Data-use crawler controls:** Lists the path-specific rules for GPTBot, ClaudeBot, Amazonbot, Applebot-Extended, Google-Extended, and MistralAI-Training separately from search access, with optional custom tokens. Applebot-Extended is evaluated as a robots policy token, not as an access-log crawler. Amazon documents Amazonbot as supporting product and service improvement and potentially AI-model training, while Amzn-SearchBot is a distinct search crawler that Amazon says does not crawl for generative-AI model training. These controls serve different product purposes. A site's training/data-use preference is not the same as permission for a search crawler to retrieve a page.
- **Robots-controlled user-triggered fetches:** Separately checks MistralAI-User because Mistral documents its robots policy as controlling whether Vibe user requests can fetch a site's pages. This access result is not folded into search or model-training policy coverage. Other user-triggered fetchers remain not applicable unless their operator documents a robots-controlled policy.
- **Search preview and data-use controls:** Reports HTTP status and page-level `noindex`, `nosnippet`, `max-snippet:0`, and `data-nosnippet` signals. It separately records crawler-scoped `noindex` and `noarchive` directives for data-use crawlers that retrieve pages, including directives scoped to `Amazonbot` in a meta tag or `X-Robots-Tag`; policy-only tokens such as Applebot-Extended and Google-Extended are not treated as page crawlers for this inventory. Baseline and sitewide GEO reports preserve these changes without treating them as search-snippet restrictions. Amazon documents `noarchive` as a way to tell Amazonbot not to use a page for model training; that meaning is provider-specific, so Aviary reports the directive rather than generalizing the semantics to other providers. For visible `data-nosnippet` regions, it counts the visible words and their share of visible content; nested marked regions are counted once for the word total. Baseline comparisons include changes to marked-region counts and word totals, while sitewide reports list affected URLs.
- **Answer-content profile:** Counts visible words, semantic `main`/`article` regions, headings, question-shaped headings followed by an 8–100-word paragraph, lists, tables, external links in the content region, visible author/date markers, the bounded declared `<html lang>` value, and JSON-LD types and author/date fields. For JSON-LD `dateModified`, it also retains up to 10 distinct valid UTC calendar days, and flags truncated or non-date values so sitemap dates can be cross-checked without retaining arbitrary date strings. It inventories literal boolean `isAccessibleForFree` declarations, distinguishing `true`, `false`, conflicting booleans, and no boolean declaration; non-boolean values are separately reported. Apple says `isAccessibleForFree:false` leaves Apple Search eligibility intact but excludes page content from additional context for Apple AI outputs; it also documents that `nosnippet` prevents Applebot from using page content as additional AI context. Aviary labels these Apple-specific observations separately and treats them as informational controls, not search-access failures or citation predictions. Sitewide summaries count each declaration state, baseline diffs report changes to the per-page value, and Applebot log correlations distinguish both the structured-data and `nosnippet` signals. The language is the page's declaration, not automatic identification of its prose.
- **Source/rendered content profile:** Compares up-to-five-word text sequences in the initial HTML response with the browser-rendered page, reporting overlap and counts without retaining page text. It analyzes initial HTML only when the response body is at most 2 MiB, then limits each leading text sample to 1,000,000 characters and 25,000 words. The check reports when either text cap is reached. Hidden markup, late updates, personalization, and text normalization can also affect overlap. This is a rendering-difference signal from Aviary's browser session, not a simulation of a named crawler or an indication that a particular engine cannot render JavaScript.
- **Citation and evidence profile:** Counts external source links and distinct hosts, descriptive link labels, links below headings such as “References” or “Sources,” citation-shaped in-page links, and JSON-LD blocks containing a `citation` field. It ranks up to 12 external hosts by observed link count per page and reports the leading host’s share, with truncation indicators. When a page has at least five observed external links and one host accounts for 80% or more, recommendations add a low-priority prompt to review whether the source mix fits the evidence; this does not score source quality. It also checks whether fragment targets used by citation-shaped in-page links exist in the rendered DOM, and counts resolved markers whose reference element contains an external source link versus those without one. A missing outgoing link is only a structural observation, not proof that a citation is invalid. It reports unresolved fragments with up to 10 examples of at most 200 characters each. This is a DOM snapshot check; scripts may add targets later, and it does not fetch or verify external sources or determine whether a source supports a claim.
- **Optional `llms.txt` inventory:** Checks for `/llms.txt` and `/llms-full.txt` only when robots.txt allows AviaryBot. It reads at most 64 KiB per file and reports status, content type, headings, links, and non-empty lines. Missing files are informational; the convention is not required for Google Search.

For found `llms.txt` and `llms-full.txt` files, the bounded inventory also profiles Markdown link targets without fetching them: it counts same-origin and external HTTP(S) links, relative references, unique and repeated web destinations, unsupported schemes, invalid destinations, empty labels, and malformed link candidates. These counts describe only the first 64 KiB when the file is larger, and target strings are not retained. It recognizes inline `[label](destination)` syntax only; reference-style links and escaped Markdown are not parsed. Relative references that resolve to the file origin also count as same-origin links, so the categories can overlap. Use them to inspect file structure; they do not verify link availability or recommend that the optional convention be adopted. The content and evidence profiles are diagnostic inventories. Batch reports aggregate answer-content structure, source/rendered phrase coverage, visible and schema author/date signals, schema types, organization/person/brand identity nodes with `@id` values, and hosts referenced by their `sameAs` properties. They also count pages with unresolved in-page citation targets and retain up to 10 fragment examples of at most 200 characters per page. The batch means are unweighted averages across pages with enough rendered text or visible words to form a sample; source/rendered phrase overlap also appears in fixed coverage bands, with pages lacking a usable rendered phrase sample counted separately so a low-coverage minority is not hidden by the mean. Sitewide author/date cross-tabs show whether visible markers and corresponding schema fields are both present, present on only one surface, or absent; they compare presence, not author identity or date-value agreement. Aviary highlights shared identity IDs with different names for review; localized or intentionally different names are not automatically errors. It also compares the complete `sameAs` link sets for shared IDs across pages and lists differing profiles as review cues; intentional page-specific modeling can explain the differences, and URLs are not verified as official profiles. Comparisons exclude page profiles whose identity or `sameAs` list hit its cap. Identity collection is capped at 20 nodes and 10 `sameAs` links per entity per page. The per-page JSON-LD type list is capped at 20 entries, and the report identifies pages that reached this cap. Hosts are counted, not verified as official identity profiles. Question-heading detection recognizes question punctuation and common opening words in several languages, but it remains a heuristic and can miss other forms. Aviary does not treat a particular word count, short answer block, citation count, author marker, schema type, or `llms.txt` file as a generative-search requirement. The question-and-paragraph pattern is a transparent heuristic for editorial review, not a claim that content should be split into artificial chunks. `data-nosnippet` counts reflect visible marked content at audit time, not whether an engine chooses to use the remaining page text.

## Read the crawler results by purpose

Search and training controls should not be conflated. OpenAI documents OAI-SearchBot for ChatGPT Search separately from GPTBot, which is used for model development. Anthropic likewise distinguishes Claude-SearchBot from ClaudeBot and its user-triggered Claude-User. Google says Googlebot controls access to Search features, while Google-Extended is a separate control for Gemini Apps and Vertex AI use; Google-Extended does not control Google Search inclusion.

The checker evaluates the current URL, not the entire site. A robots rule can allow one path and block another. An allowed robots rule is not a promise that a service will crawl, index, cite, or display the page.

## Measure actual visibility

Use each platform's own reporting tools to measure observed visibility. Google reports AI-feature traffic within Search Console's Performance report. Bing Webmaster Tools' AI Performance report provides publisher citation observations across supported Microsoft AI experiences. These platform measurements answer questions that a one-page technical audit cannot.

`--geo-answer-source-persistence-csv reports/source-persistence.csv` measures citation-domain retention from one captured timestamp to the next for the same normalized exact prompt. The CSV reports retained/lost next-timestamp transitions, reappearances after absence, mean interval to the next sample after a citation, longest runs of sampled timestamps, and source presence at each prompt series boundary. This workflow accepts a single-page report, URL batch report, or sitewide GEO summary. It evaluates every unique valid same-origin audited URL up to 8,192 characters against built-in search and data-use crawler groups, including the Google-Extended robots policy token and MistralAI-User as a documented robots-controlled user fetch, with exact path and query matching. Google-Extended is included as a data-use policy token here even though it is not distinguishable as an HTTP user-agent in access logs. Query values and fragments are omitted from output; rows expose whether a query was evaluated and how many parameters it contained. `--geo-robots-token` can add up to 20 custom groups; they remain labeled custom and do not imply a known provider or crawler purpose. Add `--geo-robots-baseline-txt` to compare matched URL/token decisions, including newly blocked/allowed pages and rule changes. Add `--fail-on-newly-blocked-geo-audit-pages` to exit 1 if a comparable URL/token pair becomes blocked or if URL coverage/detail is incomplete, including non-comparable or missing pairs. The report includes the audit and robots snapshot timestamps, the robots SHA-256, per-token coverage, and bounded page-level rule explanations; it follows the [GEO robots audit replay schema](geo-robots-audit-replay.schema.json). Off-origin, invalid, overlong URLs, and failed source-audit pages are counted separately. It evaluates the supplied policy snapshot, not the policy that was active during the saved audit. Add `--html` and `--pdf` to save self-contained visual and print-ready reports; output paths must be distinct from inputs and each other.

You can evaluate sitemap-listed URLs against the same local robots snapshot without first auditing page content:

```sh
aviary --geo-robots-sitemap https://example.com/sitemap.xml \
  --geo-sitemap-max-urls 5000 \
  --geo-robots-origin https://example.com \
  --geo-robots-txt snapshots/robots-current.txt \
  --geo-robots-baseline-txt snapshots/robots-previous.txt \
  --fail-on-newly-blocked-geo-targets \
  --html reports/robots-sitemap.html
```

Sitemap discovery follows same-origin sitemap indexes, observes the live site's robots policy while fetching sitemap documents, and caps the returned URL list at 10,000. The discovered page URLs are evaluated against the supplied robots snapshot; their page content is not fetched. Sitemap and robots origins must match. Query values and fragments from listed URLs are omitted from output, though query presence and parameter counts remain. Reaching the configured URL cap marks the list as potentially incomplete; the generic release gate treats that as incomplete coverage and fails closed. The report records whether targets came from a sitemap or a saved audit, includes the sitemap URL without its query string, and retains the existing version 1 schema with additive source fields.

Treat these as observations of the supplied log format and time range. A user-agent string can be spoofed; verify requests by provider IP or official verification tools before allowlisting, blocking, or attributing traffic. A 2xx response says the logged request succeeded at that layer, not that the page was indexed or cited. A sampled access log does not prove no request occurred. Google-Extended has no distinct user-agent string and cannot be separated from Googlebot traffic this way. MistralAI-Index, MistralAI-Training, and MistralAI-User are classified as search, training, and user-triggered fetch respectively from Mistral's first-party documentation. Sources: [Amazon's crawler guide](https://developer.amazon.com/amazonbot), [Apple's About Applebot guide](https://support.apple.com/en-gb/119829), [Google's crawler list](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers), [Bing's crawler overview](https://www.bing.com/webmasters/help/which-crawlers-does-bing-use-8c184ec0), [OpenAI's crawler overview](https://developers.openai.com/api/docs/bots), [Anthropic's crawler guide](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler), [Perplexity's crawler documentation](https://docs.perplexity.ai/guides/bots), and [AWS's CloudFront standard log reference](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html).

For Cloudflare JSONL, `SecurityAction` and `SecurityActions` provide per-crawler counts of logged blocking, challenge, solved/bypassed challenge, allow/bypass/skip, and other actions. Failure hotspots cross-reference 4xx/5xx outcomes on each path with logged block and challenge classes. Multiple classes can occur on one request; these fields show that security actions and a response status co-occurred in the sample, not which action caused a particular response. Missing action fields mean unknown coverage, not that the edge allowed every request. See Cloudflare's [HTTP request log field reference](https://developers.cloudflare.com/logs/logpush/logpush-job/datasets/zone/http_requests/).

Compare a saved crawler-log report with a later sample using `--geo-crawler-baseline-json`. Aviary normalizes request and failure shares within each crawler sample and highlights failure emergence/clearance, response-class shifts, status-code and media-type changes, request-share shifts, and changes in Cloudflare bot-verification/security-action coverage when those fields are present in the exports. It also compares tagged AI referral request counts, failure rates, and retained paths by configured source label, plus counts of configured, unconfigured, conflicting, and empty/oversized UTM markers. Unmatched source values stay private and are not assumed to be AI traffic. Keep the exact UTM mappings the same across both samples; an old report without referral data, a source label, or UTM marker-coverage fields is shown as unavailable, not zero. For multiple input logs, pair baseline and current analyses by their order in the saved JSON and current arguments. Each report retains at most 200 paths per crawler and 100 paths per referral source; current-only and baseline-only paths are list differences, not evidence that crawl activity began or stopped. Period lengths and log coverage affect raw volume, recency, failure rates, and Cloudflare coverage counts.

If both periods include CloudFront result fields, the comparison also shows each logged category's share among requests carrying that field and the share of paired rows where `x-edge-result-type` differs from `x-edge-response-result-type`. The field denominators are reported separately, and absent coverage is unknown rather than zero. Treat changes as a prompt to inspect the matching log and CDN configuration; they are not by themselves proof of a GEO or cache regression.

The same crawler-log report can measure explicitly tagged referral requests. Aviary recognizes OpenAI's documented ChatGPT `utm_source=chatgpt.com` marker by default; use repeatable `--geo-ai-referral-source <label=value>` options for other exact UTM values already used in your attribution links. For example, `--geo-ai-referral-source Perplexity=perplexity.ai` labels only requests whose `utm_source` value exactly matches `perplexity.ai`; it does not assert that this is a provider-defined marker. The report groups tagged requests by label, normalized request path, response class, logged response media type, and UTC day. Media types are response-header observations; they do not assess body quality or prove that a page was usable to an AI system. It drops query strings and raw UTM values, counts HTTP request rows rather than sessions or visitors, and cannot establish that an AI system cited the page. An attribution-coverage summary counts configured matches, unconfigured single values, conflicting repeated values, and empty or oversized markers without exposing unmatched values or assuming they indicate AI traffic; CLI and HTML views show the marker share of all parsed request rows. Missing markers mean unknown attribution, not zero referrals. OpenAI documents the ChatGPT UTM marker in its [publisher FAQ](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq).

Failure-hotspot rows carry the path's bounded status, origin-status, response media-type, and timestamp profile alongside failure shares and Cloudflare evidence. Since hotspots are computed across all paths in the input, low-volume failures can appear outside the ordinary frequent-path table.

Use `--fail-on-new-geo-crawler-failures` to turn the period comparison into a CI gate. It exits with status 1 if a retained path gains 4xx/5xx responses, a crawler's aggregate failure rate rises, or retained-path comparison detail is incomplete. Keep the two samples similarly scoped; this is a log-sample regression check, not a provider crawl guarantee.

Use `--fail-on-new-ai-referral-failures` with the same saved baseline to gate configured tagged-referral paths. It exits 1 when a source's aggregate 4xx/5xx rate rises, a shared retained path gains failures, or source/path comparison data is missing or truncated. The gate checks raw counts for the rate comparison, even though displayed percentages are rounded to one decimal place. Configure identical source labels and exact UTM values in both periods. Current-only retained paths stay incomparable to baseline and are not called newly failed; sample length, query tagging, and mapping changes affect interpretation.

Use `--fail-on-ai-crawler-timing-regression` to gate comparable crawler response timing. It requires a saved crawler-log baseline and current log inputs, then exits 1 if any crawler's response-duration or time-to-first-byte p95 band moves slower. Each compared metric needs at least 20 valid timing rows in both samples; if none qualify, the gate fails because timing coverage is insufficient. Keep log format, timing field, origin, and sample scope consistent between periods because logger definitions differ and the comparison uses approximate bands.

For CloudFront result fields, `--fail-on-ai-crawler-cloudfront-result-regression` gates increases in `Error`, `CapacityExceeded`, and `LimitExceeded` shares for claimed crawler tokens. Each field needs at least 20 observations in both samples, and the gate fails closed if neither field can be compared. This is an edge-log regression signal; investigate status codes and CDN logs before attributing a cause.

### Prioritize observed GEO review work

When crawler logs are joined to a saved GEO audit, the report adds a bounded priority review queue of matched crawler-path rows. It ranks by request share within each crawler token sample, then by raw request count and the number of measured review prompts. The report shows both the path requests and the token sample denominator. Prompts include current crawler blocks or snippet/indexing controls, an Amazonbot-scoped `noarchive` directive, logged 4xx/5xx responses, and measured content or citation-evidence signals such as missing answer structures, missing visible author/date markers, absent source links, or unresolved citation targets. The noarchive prompt is limited to Amazonbot because Amazon documents that token-specific meaning for this directive. It only flags measured zeros or explicit failures; unmeasured and not-run profiles are not treated as deficiencies. Use the queue to choose pages for human review, not as a GEO score or a claim that any individual signal improves AI citations. The logs and page audit are separate time-bound observations, and the queue indicates when its 100-row cap or input coverage limits completeness. The version 1 crawler-log schema includes `priorityReviewQueue` and per-row `reviewSignals`.

### Captured-list completeness in category prompt exports

`--geo-answer-source-category-prompt-coverage-csv` and `--geo-answer-source-category-prompt-details-csv` retain positive category and owned-domain sightings even when captured lists are incomplete. Unobserved categories and owned domains remain unknown when any contributing list is incomplete, its completeness metadata is missing in an older report, or retained domain detail is capped. Those unknown states are excluded from paired absence/change denominators; complete-comparison flags are withheld when capture completeness is incomplete or unknown.

Coverage CSV separates `incomplete_captured_citation_list_prompt_groups` and `unknown_captured_citation_list_completeness_prompt_groups` from top-domain-cap counts. Aggregate comparison unknown fields are named `unknown_shared_prompts_due_to_incomplete_evidence` and `unknown_shared_category_owned_state_due_to_incomplete_evidence`, replacing the earlier cap-only names. Detail CSV includes `captured_citation_list_completeness` (`complete`, `incomplete`, or `unknown`) and explicit unknown absence states. These columns describe supplied capture evidence, not unseen provider behavior.
