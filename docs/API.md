# Aviary REST API

Aviary's REST API accepts asynchronous batch audits, reports URL-level progress, and retains completed job reports in memory. The API is useful when a service needs to request scans without running a browser itself.

Completed job reports use the [batch audit JSON shape](./audit-batch-report.schema.json); successful URL results contain [single-page audit reports](./audit-report.schema.json), while failed URLs retain their error message.

`evaluateSEOAuditGeoChangeGate(comparison, { filters, currentFailedUrls, baselineFailedUrls })` returns machine-readable `failureReasons` with stable codes (`no-comparable-data`, `unassessed-pages`, `selected-changes`, `current-audit-errors`, and `baseline-audit-errors`) and human-readable messages. `passed` is true exactly when `failureReasons` is empty.

For CLI pipelines, `--geo-gate-output result.json` writes the same evaluation plus single-page or batch scope, baseline/current timestamps, comparability basis, and normalized filters. Single-page artifacts identify both compared URLs. The option requires `--fail-on-geo-change`; output follows [`geo-change-gate.schema.json`](./geo-change-gate.schema.json), with [single-page](../examples/geo-change-gate.example.json) and [batch](../examples/geo-change-gate.batch.example.json) samples.

`assessAiAnswerCitationPagePairedReachDropGate(comparison, thresholdPercentagePoints, alpha, minimumComparablePromptGroups, metric)` enforces the same bounds as the CLI: a 0–100 percentage-point threshold, alpha in `(0, 1]`, an integer support floor from 2 to 100,000, and one of the three supported reach metrics. Invalid parameters throw before any assessment is returned.

The exported source-category monthly JSD, HHI, share-drop, and prompt-balanced JSD gate functions also validate direct Node.js inputs: divergence/HHI thresholds stay within their mathematical 0–1 ranges, share changes stay within 0–100 percentage points, support floors are bounded integers, and category basis must be `all-citations` or `top-three` where applicable.

`assessAiCrawlerPathFamilyFailureRise(...)` reports total `matchedFamilies`, `matchedFamiliesBelowSupport`, eligible `matchedFamiliesCompared`, and `supportInsufficient` when no route family is eligible. This is separate from `incomplete`, which indicates path/output truncation, so library callers can distinguish no overlap, low traffic, and capped results.

The machine-readable contract is available at [`openapi.yaml`](./openapi.yaml) and from a running server at `GET /openapi.yaml`.

## Start the server

Build Aviary, then start the API listener:

```sh
pnpm run build:ts
pnpm run api-server
```

The default listener is `http://127.0.0.1:3333`. It binds to loopback and does not require a key. To require a key on a local listener, set `AVIARY_API_KEY` to a random secret of at least 24 characters. Every `/v1` route then requires `Authorization: Bearer <key>`.

Audit URLs are opened by a real browser on the API host. A caller with API access can therefore cause that host to connect to any HTTP or HTTPS target it can reach, including private-network services. Keep API access limited to trusted operators. If clients are not fully trusted, run Aviary in a network sandbox with outbound rules that match the URLs those clients are allowed to audit. Private-site audits are supported, so Aviary does not globally block private addresses.

See the [data-handling guide](./PRIVACY.md) for what URL and report data the server retains and how optional semantic analysis uses page content.

Non-loopback binds require both a bearer key and TLS certificate and private key. The service rejects a remote bind if either is missing:

```sh
export AVIARY_API_HOST=0.0.0.0
export AVIARY_API_PORT=3333
export AVIARY_API_KEY='replace-with-a-random-secret-at-least-24-characters'
export AVIARY_API_TLS_CERT=/path/to/fullchain.pem
export AVIARY_API_TLS_KEY=/path/to/private-key.pem
pnpm run api-server
```

The CLI handles `SIGINT` and `SIGTERM` by rejecting new API requests, cancelling queued jobs, aborting active audits, closing SSE streams, and stopping the listener. Shutdown waits for active audit cleanup. Programmatic servers can use `stopAviaryApiServer(server)` for the same sequence; repeated calls share the same shutdown operation.

The `AVIARY_HEADLESS`, `AVIARY_TIMEOUT`, `AVIARY_SETTLE_AFTER_NAVIGATION_MS`, `AVIARY_VIEWPORT`, `AVIARY_PRESET`, `AVIARY_CATEGORIES`, and `AVIARY_CONCURRENCY` settings provide defaults for each job. The API-specific limits are:

| Variable | Default | Bound |
| --- | ---: | ---: |
| `AVIARY_API_MAX_BATCH_URLS` | 100 | 1–1,000 |
| `AVIARY_API_MAX_CONCURRENT_JOBS` | 2 | 1–8 |
| `AVIARY_API_MAX_PENDING_JOBS` | 10 | 0–100 |
| `AVIARY_API_MAX_STORED_JOBS` | 100 | 1–10,000 |
| `AVIARY_API_RATE_LIMIT_REQUESTS` | 60 | 1–100,000 per IP and window |
| `AVIARY_API_RATE_LIMIT_WINDOW_MS` | 60,000 | 1,000–86,400,000 |

Completed, failed, and cancelled jobs expire one hour after their last update; the expiry sweep runs on API requests, and capacity pressure can evict terminal records sooner. A process restart clears the job store. Queue capacity, retained records, and open event streams are bounded.

## Submit an audit

`POST /v1/audits` accepts exactly one source: a list of page URLs, a sitemap, or a starting page for same-origin link discovery.

```sh
curl -sS http://127.0.0.1:3333/v1/audits \
  -H 'Content-Type: application/json' \
  -d '{"urls":["https://example.com/","https://example.com/about"],"concurrency":2,"categories":["metaTags","accessibility"]}'
```

For sitemap discovery:

```sh
curl -sS http://127.0.0.1:3333/v1/audits \
  -H 'Content-Type: application/json' \
  -d '{"sitemap":"https://example.com/sitemap.xml","maxUrls":250,"concurrency":3,"navigationWaitUntil":"domcontentloaded","settleAfterNavigationMs":1500}'
```

For bounded link discovery when no sitemap is available:

```sh
curl -sS http://127.0.0.1:3333/v1/audits \
  -H 'Content-Type: application/json' \
  -d '{"crawl":"https://example.com/","maxUrls":250,"maxDepth":2,"maxPageBytes":5242880,"maxTotalBytes":262144000,"concurrency":2}'
```

The server returns `202 Accepted`, a job `id`, and a `links.self` resource path. Explicit URL lists are limited by `AVIARY_API_MAX_BATCH_URLS`. Sitemap and crawl requests default to that same page limit; `maxUrls` can lower it. Sitemap discovery follows nested same-origin indexes, accepts gzip-compressed sitemap files, and filters page URLs through the source's `robots.txt` rules. Link discovery starts from `crawl`, follows static same-origin HTML anchors up to `maxDepth` (default 2, maximum 32), and honors `nofollow` directives and the `robots.txt` policy for `AviaryBot`. Discovery requests and browser audits of discovered pages use that user agent. It does not execute JavaScript.

Request fields:

| Field | Type | Description |
| --- | --- | --- |
| `urls` | `string[]` | Unique HTTP or HTTPS URLs; 1 to the configured batch maximum. |
| `sitemap` | `string` | HTTP or HTTPS sitemap URL. Use instead of `urls`. |
| `crawl` | `string` | HTTP or HTTPS starting page for bounded same-origin HTML link discovery. Use instead of `urls` or `sitemap`. |
| `maxUrls` | `integer` | Page limit for `sitemap` or `crawl` requests. |
| `maxDepth` | `integer` | Link hops for `crawl` requests, from 0 to 32. |
| `maxPageBytes` | `integer` | Per-page HTML body limit for `crawl` requests, from 1 byte to 10 MiB; defaults to 2 MiB. |
| `maxTotalBytes` | `integer` | Combined HTML discovery response limit for `crawl` requests, from 1 byte to 1 GiB; defaults to 100 MiB. |
| `concurrency` | `integer` | Browser audits per job, from 1 to 8. |
| `timeout` | `integer` | Navigation timeout in milliseconds, up to 300,000. |
| `navigationWaitUntil` | `domcontentloaded \| load \| networkidle` | Browser navigation readiness condition; defaults to `networkidle`. Earlier events can accommodate pages with persistent requests but may precede late client-rendered content. |
| `settleAfterNavigationMs` | `integer` | Fixed delay after navigation readiness, 0–30,000 ms; defaults to 1,000 ms. Successful page reports echo the selected value. |
| `preset` | `basic \| advanced \| strict \| geo` | Checker preset override; `geo` enables only AI discoverability checks. |
| `categories` | `string[]` | Unique checker category keys to run. |

URLs must not contain embedded credentials and are limited to 2,048 characters. Request bodies are capped at 3 MiB. Sitemap pages and crawl links stay on the source origin. Crawl pages are limited to 2 MiB each and 100 MiB combined by default, with 10,000 candidate links per page; inaccessible or non-HTML pages are skipped. Set `maxPageBytes` up to 10 MiB and `maxTotalBytes` up to 1 GiB to adjust those discovery-body limits. If the aggregate limit is reached before discovery completes, the job fails instead of auditing a partial discovery result. If robots.txt disallows every sitemap URL, the job fails with an explanatory error instead of returning an empty audit report. If robots.txt is unreachable or returns a server error, link discovery stops instead of continuing without its policy.

## Read progress and results

Poll `GET /v1/audits/{id}` using the `Location` response header or `links.self` path. The job `status` is `queued`, `running`, `completed`, `failed`, or `cancelled`. The response includes `progress.completedUrls`, `progress.requestedUrls`, and, after an audit finishes, a `report` with the batch results. Successful page reports echo `navigationWaitUntil` and `settleAfterNavigationMs` so saved reports record navigation and client-rendering timing. During sitemap or link discovery, `requestedUrls` grows as pages are found and `completedUrls` remains zero.

```sh
curl -sS http://127.0.0.1:3333/v1/audits/JOB_ID
```

`GET /v1/audits/{id}/events` streams Server-Sent Events. Each `update` event has an `id` equal to the monotonically increasing revision and JSON data containing the current status and progress. After a running cancellation request, updates include `cancelRequested: true` while the job stops. A heartbeat comment is sent every 15 seconds. The stream closes at a terminal status. The server accepts up to 100 concurrent event streams.

```sh
curl -N http://127.0.0.1:3333/v1/audits/JOB_ID/events
```

The JSON report omits inline base64 heatmap screenshots to keep retained job data smaller; check results and heatmap geometry are retained. Cross-page hreflang reciprocity, canonical consistency, and GEO coverage are available to Node.js callers through `analyzeSiteWideHreflang(report)`, `analyzeSiteWideCanonicals(report)`, and `analyzeSiteWideGeo(report)`. The GEO aggregate includes sitewide counts, compact normalized `pageSummaries`, answer-content profile counts, schema-type coverage, shared entity-ID name and normalized @type variants, and differing complete `sameAs` link sets (up to 50 findings and 50 page observations each), sameAs host coverage, bounded per-page external-source host link counts, leading-host share, unresolved in-page citation target counts, and the exact URLs with `noindex` or no-snippet controls; per-page JSON-LD type lists are capped at 20, and the aggregate reports pages that hit the cap. sameAs comparisons omit page profiles with capped identity or sameAs inventories. Page summaries also retain up to 10 distinct, normalized UTC calendar days for literal JSON-LD `dateModified` values, plus flags for additional or non-date values; they retain no arbitrary date strings. These are structural observations, not known generative-search requirements. `--geo-summary-output` writes this aggregate for batch audits as JSON with `schemaVersion: 1` and the source audit timestamp; `--geo-summary-csv` writes a companion page-level spreadsheet export with explicit coverage-status columns, visible-versus-schema author/date/accessibility signals, document-language validity, per-crawler preview controls, citation target resolution, bounded source-host link profiles, and formula-safe cell quoting. `--geo-crawler-access-csv` writes normalized page, policy, and crawler rows, including preview-only crawler tokens, with separate access/preview coverage, preview-only tokens, and no conflation of search directives with user-fetch policy. `--geo-entity-variants-csv` exports cross-page structured-identity differences into CSV, using page-level rows for type and `sameAs` observations and an entity-level page list for name variants, with audit-wide truncation counters and exported-versus-total variant counts in a summary row. The JSON output follows [`docs/geo-summary.schema.json`](geo-summary.schema.json). `--geo-comparison-csv` exports one summary row and one row per changed GEO signal when a baseline is supplied. The CLI also checks supplied version 1 summaries for valid page-signal types and ranges, including trimmed, unique search/data-use/user-fetch crawler tokens, HTTP status codes, data-nosnippet word/share denominator consistency, citation evidence, calendar-valid `dateModified` samples, identity entities, rendered-content assessment reasons, and unique optional-file paths with complete link profiles, before using them in GEO comparisons. Page summaries expose observed crawler rules and preview controls, per-token data-use `noindex` and `noarchive` observations, content counts, source/rendered coverage, citation evidence, and optional-file states without retaining page text or producing a GEO score. Citation evidence includes bounded samples of in-page citation fragments whose targets were not present in the rendered DOM snapshot, plus counts of resolved reference elements with and without an external source link. Each page's `signalCoverage` distinguishes measured, not-assessed, and not-run profiles; `signalNotes` carries available assessment reasons. `parseBingAiPerformanceCsvExport(csvText)` reads a local Bing Webmaster AI Performance CSV export without making network requests; `summarizeBingAiPerformanceExport(exportData)` ranks rows, groups topic and intent dimensions, and summarizes date buckets within one export view; `correlateBingAiCitationsWithAudit(exportData, audit)` matches cited pages to a saved single-page report, batch report, or version 1 GEO summary by exact URL or a unique audited canonical URL. Its row-level `auditMatchType` distinguishes exact, canonical, ambiguous normalized audit URL, ambiguous canonical, and unmatched URLs; ambiguous normalized URLs and canonical targets do not inherit crawler controls. Correlation results include current `bingbot` indexing and snippet directives, page-wide snippet restrictions, and visible `data-nosnippet` counts when present in the audit. The GEO summary aggregates per-crawler allow/block counts, snippet restrictions, optional `llms.txt` files, citation-shaped content signals, and observed source-host coverage across completed pages. `filterSEOAuditGeoSignalChanges(changes, { signals, urls, transitions })` applies the CLI GEO gate’s exact, case-sensitive signal, URL, and before/after transition filters in Node.js; repeated values within each dimension are alternatives, while supplied dimensions combine. `evaluateSEOAuditGeoChangeGate(comparison, { filters, currentFailedUrls, baselineFailedUrls })` evaluates comparability, selected changes, and batch audit failures using the same fail-closed rules as the CLI. See [`examples/geo-filter-report-comparison.ts`](../examples/geo-filter-report-comparison.ts) for an offline single-page example. `compareSEOReports(current, baseline)` and `compareSEOAuditBatches(current, baseline)` include `geoChanges` for crawler access and matching-rule/group changes, page indexing/snippet and data-use `noindex`/`noarchive` controls, answer-content and citation-evidence profile differences including source-host distributions and resolved citation-target links, JSON-LD types and named identity entity changes, source/rendered phrase coverage, optional-file availability, and normalized `dateModified` day changes on matched pages. `geoCompared` indicates whether both single-page reports contain comparable search-crawler access and preview-control inputs; `geoChanges` can also contain deltas for other individually measured GEO signals. Both single-page and batch comparison JSON objects follow the [GEO report comparison schema](geo-report-comparison.schema.json), include `schemaVersion: 1` and `geoComparedBasis`, with the value `search-crawler-access-and-preview-controls`; the basis is exported as `GEO_COMPARABILITY_BASIS`, and `GEO_COMPARISON_SCHEMA_VERSION` exports the comparison version. The GEO comparison CSV includes `schema_version` and repeats `geo_comparability_basis` on summary and change rows. The batch comparison exposes `geoComparedPages` and `geoUnassessedPages` for matched pages with and without comparable crawler-access/preview-control inputs; the CSV summary row carries those counts. These coverage counts do not describe whether every other GEO signal was measurable. These are snapshot differences, separate from failed-check regressions, and do not predict citations. CLI users can save the full comparison object separately with `--comparison-output`; single-page HTML, PDF, and Markdown baseline reports show score movement, changed checks, and GEO signal changes, while batch HTML, PDF, and Markdown reports include their existing cross-page comparisons. Single-page HTML GEO details are capped at 50 changes per finding group. Batch HTML comparison details cap each URL/finding list at 50 rows and GEO changes at 100, with truncation notices. Other batch formats retain their existing site-wide analyses. Reciprocal links, canonical chains, and loops can only be verified when the relevant target pages completed in the batch.

The sitewide source/rendered overlap mean is accompanied by fixed percentage bands from 0–19.9% through 80–100%, plus a count of profiles without a usable text sample. The distribution helps surface low-overlap pages that a mean can hide; it remains an initial-HTML/browser-render comparison, not a named crawler's rendering behavior.

Sitewide author and date cross-tabs compare the presence of each visible page marker with its corresponding structured-data field. They report both present, visible only, schema only, neither, and incomplete-profile counts. They do not retain author names or date values and therefore do not claim those values agree.

`compareBingAiPageCitationExports(current, baseline)` compares citation-count deltas and per-page average citation-share changes on URLs from two `page-citations` exports without query or date dimensions. Citation shares are averaged per URL and share changes are percentage-point differences; they are not additive counts. Citation-count comparability is reported separately from share comparability. Bing export-only URLs have unknown missing-period values because reports are sampled; comparisons should use the same property and report settings, and detail rows are capped at 1,000. `compareBingAiQueryPageMappings(current, baseline)` compares two query-page exports by case/whitespace-normalized exact phrase and normalized URL. It reports query/URL pairs observed in only one sample, and citation deltas only for shared pairs with a citation value in both exports; details are capped at 500 phrases and 10 URLs per phrase. Absence is not evidence of a true lost prompt or citation, and row sums can overlap. `analyzeBingAiQueryPageMapping(exportData, auditCorrelation?)` summarizes exact phrase-to-page mapping overlap from a query-page export, with bounded group lists; normalization is case-insensitive and whitespace-only, and the result does not diagnose cannibalization or duplicate answers. For each query group with citation values it also computes the largest page share, Herfindahl index, and reciprocal-based effective page count from only mapped URLs with available citation metrics, alongside page-metric coverage; zero-total and partial groups are called out. The report-level medians exclude groups without positive measured totals. These metrics describe a sampled mapping distribution and are not a quality or ranking score. Passing rows from `correlateBingAiCitationsWithAudit` adds each mapped URL's current audit match/access/preview/content signals and a per-query coverage summary. This describes current snapshots and does not explain why a URL appeared in a grounding-query mapping. `analyzeBingAiTopicIntentIntersections(exportData)` summarizes co-occurring topic and intent labels from rows that provide both dimensions.

The CLI Bing import JSON includes `schemaVersion: 1` and follows [`docs/bing-ai-report.schema.json`](bing-ai-report.schema.json), including when optional topic-intent analysis, query-page analysis, citation-period comparison, or audit correlation fields are present.

`renderBingAiPerformanceHtml(input)` creates an offline, searchable HTML report from the same parsed exports, summaries, optional query-page maps, citation-period comparison, and audit correlations. The renderer escapes imported values, allows only HTTP(S) page links, and does not load remote assets.

`renderGoogleAiPerformanceHtml(input)` creates a self-contained review page for Search Console Search or Discover exports, including available page/country/device/date tables, matched-page impression comparison, and current-control correlation summaries. Imported strings are escaped, page links are limited to HTTP(S) without credentials, and no remote assets are loaded.

`analyzeAiCrawlerAccessLog(text, options)` parses local Apache/Nginx combined logs, header-driven CloudFront standard tab-delimited logs, or JSONL into bounded per-crawler request, status-code, path, method, and UTC-day summaries. Its built-in Mistral catalog separates `MistralAI-Index` search requests, `MistralAI-Training` dataset crawling, and user-triggered `MistralAI-User` fetches according to Mistral's published crawler roles. CloudFront `sc-status` `000` is retained as status 0 in the `other` response class. When JSONL includes both Cloudflare `EdgeResponseStatus` and `OriginResponseStatus`, the report counts edge/origin disagreements per crawler and path to help isolate delivery-layer transformations. Cloudflare documents origin status `0` as no origin response with the response served at the edge, so a mismatch is not automatically an error. Per-path timestamps expose first/last observations and whole days before the newest parseable event for that crawler in the input; the timestamped request count reveals partial timestamp coverage. It also compares response-class availability, each path's ten most frequent HTTP codes, and five most frequent response media types for exact paths shared by recognized search-crawler tokens and, separately, training-data-crawler tokens; each comparison flags sample paths where one token receives 2xx while another receives 4xx/5xx. Comparisons use retained top paths, signal truncated status/code-type details, and do not explain the discrepancy. The separate `failureHotspots` list scans all observed paths (not just retained frequent paths), ranks up to 50 paths with 4xx/5xx responses, and exposes sample-wide and per-path failure shares plus frequent statuses; server errors rank first. Both failure rates describe only supplied logs and do not explain causes. Logged media types describe response headers rather than response-body quality. JSON field matching ignores case and punctuation and accepts common Cloudflare HTTP request log field names. It groups provider search crawlers, user-triggered fetchers, data-use crawlers, and training-only crawlers as separate activity classes. Amazon tokens distinguish search (`Amzn-SearchBot`), broad product data use (`Amazonbot`), and user-triggered fetches (`Amzn-User`). Applebot is a recognized search crawler; Applebot-Extended is kept as a robots policy token, not a logged crawler. Optional `customTokens` are returned as unclassified claims. Query strings and fragments are stripped; request hosts, IP addresses, referrers, and full user-agent strings are not retained. Matching is based on the claimed user-agent token only and does not authenticate a request. `renderAiCrawlerAccessLogHtml(analyses)` produces a searchable offline report; CLI output follows [`docs/ai-crawler-log-report.schema.json`](ai-crawler-log-report.schema.json).

`renderAiCrawlerPathFamiliesCsv(analyses, pathDepth?)` exports route-family aggregates from one or more parsed access-log analyses, with leading-segment depth 1–5 (default 2), UUID/long-ID normalization, response classes, status and content-type rollups, sample paths, and explicit retained-path/output caps. `renderAiCrawlerPathFamiliesHtml(analyses, pathDepth?)` creates a self-contained dashboard. `renderAiCrawlerPathFamiliesJsonFromCsv(csv, analyses?)` converts the bounded CSV inventory into a versioned typed JSON artifact; pass the source analyses to restore original labels that CSV spreadsheet protection may escape. When exact crawler/audit joins are available, `renderAiCrawlerPathFamilyAuditCorrelationCsv(correlations, pathDepth?)` groups their retained path observations by family and reports request-weighted audit signals with per-signal observed denominators, overlapping review-signal request counts, current-snapshot timestamps, match states, and truncation markers; `renderAiCrawlerPathFamilyAuditCorrelationHtml(correlations, pathDepth?)` visualizes match support and measured answer/citation signals. `renderAiCrawlerPathFamilyAuditCorrelationJsonFromCsv(csv, correlations?)` serializes those current-snapshot rows as typed JSON; pass correlations to retain original user-agent and source-file labels. `renderAiCrawlerPathFamilyAuditComparisonCsv(baselineCorrelations, currentCorrelations, pathDepth?)` compares current audit profiles only on exact crawler paths matched to audited pages in both snapshots, weighting shared paths equally and reporting per-signal paired support. `renderAiCrawlerPathFamilyAuditComparisonHtml(baselineCorrelations, currentCorrelations, pathDepth?)` visualizes those paired shifts offline. `renderAiCrawlerPathFamilyAuditComparisonJsonFromCsv(csv, baseline?, current?)` converts a computed comparison table without repeating its analysis and can restore labels using the supplied correlations. `renderAiCrawlerPathFamilyPeriodComparisonCsv(baseline, current, pathDepth?)` compares position-paired access-log samples by crawler and normalized route family, preserving one-period presence and suppressing deltas or retained-catalog shares where they are not comparable. `renderAiCrawlerPathFamilyPeriodComparisonHtml(baseline, current, pathDepth?)` renders those comparison rows as an offline, filterable dashboard. `renderAiCrawlerPathFamilyPeriodComparisonJsonFromCsv(csv, baseline?, current?)` preserves the bounded comparison rows as typed, versioned JSON and can restore labels using the source analyses. `assessAiCrawlerPathFamilyFailureRise(baseline, current, thresholdPercentagePoints, pathDepth?, minimumRequestsPerPeriod?)` returns matched-family 4xx/5xx share rises (default minimum 10 requests per period) and explicit path/output completeness state for CI gates. These reports summarize only retained per-crawler paths; they do not authenticate user-agent claims or connect crawl activity causally to citations.
`options.ipRanges` optionally accepts token-keyed CIDR lists. Built-in crawler tokens and explicitly configured custom tokens are accepted; log parsing recognizes the combined-log client field, CloudFront `c-ip`, and common JSON client-IP fields, but ignores forwarded-for headers. Matching uses locally supplied IPv4/IPv6 ranges, normalizes IPv4-mapped IPv6 addresses, and returns only configured-range counts plus request counts by match/missing/invalid state. Raw addresses and configured CIDRs are not emitted. Supply and update ranges independently: this is address-range membership evidence for a claimed User-Agent, not crawler authentication.
When logs provide timing, crawler, path, and UTC-day summaries include fixed-band p50/p95 observations for response duration and time to first byte. CloudFront standard fields `time-taken` and `time-to-first-byte` are interpreted in seconds; JSONL also accepts explicitly named seconds fields such as `request_time` and millisecond fields with `_ms`/`Ms` suffixes. Band percentiles are approximate, and only requests carrying recognized timing values enter their denominators. Values over 24 hours or malformed values are ignored. Logger definitions differ: for example, CloudFront measures at its server through output-queue writes, while Nginx `request_time` runs through its log write after sending the response. Keep each log file and its measurement source separate when comparing timing; these figures do not represent end-user experience.

CloudFront `x-edge-result-type` and `x-edge-response-result-type` values are optionally grouped by crawler and path. The profile lists only bounded known categories (unknown labels become `Other`) and counts paired requests whose two recorded categories differ. CloudFront defines these as classifications at two distinct points in response delivery; this profile reports logged values and is not a generic cache diagnosis. See the [CloudFront standard logging reference](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html).

The version 1 sitewide summary also carries a bounded `linkTargetProfile` for found optional `llms.txt` files and aggregates counts in `optionalLlmsFiles[].linkTargetTotals`. It classifies inline Markdown link targets locally, keeps no target strings, and does not fetch the targets. Relative references that resolve to the file origin also count as same-origin links. Profiles are limited to the first 64 KiB; the summary exposes the capped-profile count. These structural measurements do not make `llms.txt` a search requirement.

`correlateAiCrawlerAccessLogWithGeoAudit(analysis, audit, origin)` joins retained crawler request paths to exact same-origin audit paths. Matched path rows include current answer-content and citation-evidence coverage, question and answer-block counts, visible author/date markers, and source-link, inline-marker, and unresolved-target counts when those profiles were measured. Aggregate request totals count observed log requests on matched paths with each signal present; they do not sum content objects or imply crawler preference. Audit signals can postdate the log sample, and not-run/not-assessed states are preserved separately from measured zeroes.

The analysis also aggregates exact `utm_source` values into `aiReferralTraffic`, with a built-in `ChatGPT (UTM)` label for `chatgpt.com` and optional `aiReferralSources: [{ label, value }]` mappings. It returns bounded per-label request, status-class, path, logged response media-type, and UTC-day summaries while omitting raw UTM values and query strings. Media types come from logged response headers and do not assess body quality. `utmSourceAttributionCoverage` separately counts parsed request rows, configured matches, one-value markers with no configured label, conflicting repeated values, and empty or oversized values; CLI summaries derive marker share from the parsed-request denominator. It never emits unmatched values and does not assume they are AI referrals. These are matching request rows, not sessions or unique visitors; absence of the marker is unknown attribution coverage. OpenAI documents that ChatGPT adds `utm_source=chatgpt.com` to referral URLs in its [publisher FAQ](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq).

For Cloudflare JSONL fields `BotScore`, `BotScoreSrc`, and `VerifiedBotCategory`, each matched crawler summary includes optional-input coverage, Cloudflare score groups (0 not computed, 1 automated, 2–29 likely automated, 30–99 likely human), score-source counts, verified-bot request counts, and bounded category counts. `Verified Bot` score-source or a non-empty category contributes to the `verifiedBotRequests` count; these annotations are evidence from Cloudflare logs, not proof of the named user-agent identity. Each failure hotspot also reports annotated requests, verified-evidence requests, and 4xx/5xx failures among those requests; absent Cloudflare fields are unknown coverage, not evidence of spoofing. JSONL `SecurityAction` or `SecurityActions` fields add per-crawler block, challenge, completed/bypassed challenge, allow/bypass/skip, and other-action counts. ## GEO crawler-log regression gate

The CLI flag `--fail-on-new-geo-crawler-failures` requires both `--geo-crawler-baseline-json` and a current `--geo-crawler-log`. It exits with status 1 when shared retained paths gain 4xx/5xx responses, a crawler's aggregate failure rate increases, a current-only retained path has failures, or retained path comparison is incomplete. ## Cancel a job

`DELETE /v1/audits/{id}` returns `204 No Content` when it cancels a queued job. For a running job it returns `202 Accepted` with the current job snapshot and `cancelRequested: true`; Aviary aborts sitemap/link discovery or active browser pages, stops starting new URLs, and returns any completed page results in a partial report. Poll the job or follow its SSE stream until the status becomes `cancelled`. Cancelling a terminal job returns `409 Conflict`.

```ts
import { AviaryApiClient } from '@ru1vly/aviary';

const client = new AviaryApiClient({ baseUrl: 'http://127.0.0.1:3333' });
const accepted = await client.cancelAudit(jobId);
if (accepted?.cancelRequested) {
  const stopped = await client.waitForAudit(jobId);
  console.log(stopped.status, stopped.report?.summary);
}
```

## Status codes and rate limits

API errors use `application/problem+json` with `type`, `title`, `status`, `detail`, and `instance` fields.

| Status | Meaning |
| ---: | --- |
| `400` | Malformed JSON or invalid request fields. |
| `401` | Missing or invalid bearer key when authentication is enabled. |
| `202` | Cancellation requested for a running job; poll or follow SSE until it stops. |
| `204` | A queued job was cancelled immediately. |
| `404` | Unknown route or job; terminal jobs also expire from memory. |
| `409` | The job has already reached a terminal state and cannot be cancelled. |
| `413` | Request body exceeds 3 MiB. |
| `429` | Per-IP request limit exceeded. Check `Retry-After`. |
| `503` | Queue, retained-job capacity, rate-limit capacity, or event-stream capacity reached. Check `Retry-After`. |

`/v1` responses include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. The reset value is a Unix timestamp in seconds. `GET /health` and `GET /openapi.yaml` are available without authentication and are outside the `/v1` rate limit.

## Typed Node.js client

The package exports `AviaryApiClient` for creating jobs, polling, waiting, cancellation, and SSE updates:

```ts

const client = new AviaryApiClient({
```

## GEO crawler-log regression gate

The CLI flag `--fail-on-new-geo-crawler-failures` requires both `--geo-crawler-baseline-json` and a current `--geo-crawler-log`. It exits with status 1 when shared retained paths gain 4xx/5xx responses, a crawler's aggregate failure rate increases, a current-only retained path has failures, or retained path comparison is incomplete. ## Cancel a job

`DELETE /v1/audits/{id}` returns `204 No Content` when it cancels a queued job. For a running job it returns `202 Accepted` with the current job snapshot and `cancelRequested: true`; Aviary aborts sitemap/link discovery or active browser pages, stops starting new URLs, and returns any completed page results in a partial report. Poll the job or follow its SSE stream until the status becomes `cancelled`. Cancelling a terminal job returns `409 Conflict`.

```ts
import { AviaryApiClient } from '@ru1vly/aviary';

const client = new AviaryApiClient({ baseUrl: 'http://127.0.0.1:3333' });
const accepted = await client.cancelAudit(jobId);
if (accepted?.cancelRequested) {
  const stopped = await client.waitForAudit(jobId);
  console.log(stopped.status, stopped.report?.summary);
}
```

## Status codes and rate limits

API errors use `application/problem+json` with `type`, `title`, `status`, `detail`, and `instance` fields.

| Status | Meaning |
| ---: | --- |
| `400` | Malformed JSON or invalid request fields. |
| `401` | Missing or invalid bearer key when authentication is enabled. |
| `202` | Cancellation requested for a running job; poll or follow SSE until it stops. |
| `204` | A queued job was cancelled immediately. |
| `404` | Unknown route or job; terminal jobs also expire from memory. |
| `409` | The job has already reached a terminal state and cannot be cancelled. |
| `413` | Request body exceeds 3 MiB. |
| `429` | Per-IP request limit exceeded. Check `Retry-After`. |
| `503` | Queue, retained-job capacity, rate-limit capacity, or event-stream capacity reached. Check `Retry-After`. |

`/v1` responses include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. The reset value is a Unix timestamp in seconds. `GET /health` and `GET /openapi.yaml` are available without authentication and are outside the `/v1` rate limit.

## Typed Node.js client

The package exports `AviaryApiClient` for creating jobs, polling, waiting, cancellation, and SSE updates:

```ts
import { AviaryApiClient } from '@ru1vly/aviary';

const client = new AviaryApiClient({
  baseUrl: 'http://127.0.0.1:3333',
  // apiKey: process.env.AVIARY_API_KEY,
});

const job = await client.audit(
  { crawl: 'https://example.com/', maxUrls: 250, maxDepth: 2 },
  { maxWaitMs: 10 * 60_000, onUpdate: (progress) => console.log(progress.status, progress.progress) },
);

if (job.status === 'completed') console.log(job.report?.summary);
```

Use `createAudit()` and `getAudit()` for manual polling, `streamAudit()` for progress events, and `cancelAudit()` for queued or running jobs. `cancelAudit()` returns `undefined` when a queued job was cancelled immediately, or the updated job snapshot when a running cancellation was accepted. Client requests accept an `AbortSignal`; `waitForAudit()` backs off between polls and retries rate-limit or temporary capacity responses. API failures throw `AviaryApiError`, which exposes the HTTP `status`, parsed problem document, and optional `retryAfterMs`.

The GEO check `source-rendered-content-profile` compares short text sequences from the initial HTML response with the browser-rendered document. It stores counts and overlap percentages, not the source text. Sitewide summaries expose `sourceRenderedProfilesAssessed`, `sourceRenderedPhraseCoverageSamples`, and the unweighted `sourceRenderedPhraseCoverageMeanPercent`. `ai-search-preview-controls` also reports visible `data-nosnippet` element and word counts; `analyzeSiteWideGeo(report)` aggregates those as `pagesWithDataNoSnippetRegions`, `totalDataNoSnippetElements`, and `totalDataNoSnippetWords`, plus the affected page URLs and the mean word share (`dataNoSnippetWordShareSamples`, `dataNoSnippetWordShareMeanPercent`). This describes one browser snapshot and does not simulate a search or AI crawler.

GEO content profiles inventory literal boolean JSON-LD `isAccessibleForFree` values in sitewide summaries and baseline diffs, retaining true, false, conflicting, and undeclared states plus a separate non-boolean-value flag. Applebot log correlation surfaces observed requests on audited pages marked `false` as a provider-specific review prompt and labels page-level `nosnippet` separately because Apple documents that directive as suppressing AI context. Apple documents that this setting does not remove the page from Apple Search, but prevents its content from being used as additional context for Apple AI outputs. These fields are optional in the version 1 summaries for compatibility and are observations, not citation predictions.

Sitewide GEO summaries also report `userInitiatedFetchPolicy` and a distinct per-page `userInitiatedFetchAccess` signal for documented robots-controlled user fetchers. Aviary currently includes MistralAI-User here because Mistral says its robots tags govern which sites Vibe can fetch at a user request; other user-triggered agents are not assumed to follow the same rule. Baseline diffs and crawler-log correlations preserve this as a separate access class.

```ts
const server = await startAviaryApiServer();
```
